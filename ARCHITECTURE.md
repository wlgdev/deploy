# Архитектура централизованного деплоя wlgdev (v1)

Централизованная система автоматического развёртывания сервисов организации `wlgdev`: headless (боты, воркеры) и веб-сервисов за Nginx Proxy Manager.

## Компоненты системы

```text
wlgdev/deploy (Центральный репозиторий)
├── .github/actions/deploy/action.yml  # Composite Action для вызова из клиентских репозиториев
├── .github/actions/publish/action.yml  # Composite Action для сборки и публикации образов в ghcr.io
├── .github/workflows/deploy.yml       # Центральный workflow: валидация, checkout, SSH-деплой
└── scripts/check-server.sh            # Скрипт проверки готовности сервера

Репозиторий проекта                    # Клиент: сборка Docker-образа и запуск Action
Целевой сервер                         # Docker host: пользователь deploy, директории /data/apps/<app>[-dev]
```

## Ключевые решения

- **`workflow_dispatch` вместо `workflow_call`**:
  `workflow_call` выполняется в контексте вызывающего репозитория, что делает недоступными секреты инфраструктуры. `workflow_dispatch` запускается в доверенном контексте центрального репозитория и позволяет выполнять ручной перезапуск или откат на любой коммит через веб-интерфейс GitHub.
- **Интегрированный Composite Action**:
  Клиентские проекты подключают готовый экшен `wlgdev/deploy/.github/actions/deploy@main`. Экшен инициирует деплой, опрашивает статус центрального запуска и возвращает реальный результат деплоя со ссылкой на логи.
- **Изоляция секретов (Least Privilege)**:
  Сервисные репозитории не имеют доступа к SSH-ключам и хостам сервера. Им выдаётся только ограниченный токен с правами на запуск workflow в `wlgdev/deploy`.
- **Разделение окружений**:
  Стеки изолированы по каталогам: `/data/apps/<app>` для продакшена и `/data/apps/<app>-dev` для dev-версий.
- **Безопасность переменных окружения (Transient env)**:
  Переменные передаются через временный файл `.env.tmp` с правами `600`, экспортируются в текущую bash-сессию на время выполнения команд и сразу удаляются с диска.
- **Интеграция с Nginx Proxy Manager (v3)**:
  Если задан параметр `target`, пайплайн генерирует `docker-compose.override.yml`: сервисы из `target` подключаются к собственной внешней Docker-сети стека `proxy-<app>-network` (dev: `proxy-dev-<app>-network`), в которой постоянно живёт контейнер Nginx Proxy Manager, и получают уникальный DNS-алиас `<стек>-<сервис>` (например `dummy-deploy-hello`), чтобы имена не конфликтовали между стеками.
  Отдельным шагом после `docker compose up` пайплайн синхронизирует proxy hosts в Nginx Proxy Manager через его REST API (CLI [`npm-api.sh`](https://github.com/Erreur32/nginx-proxy-manager-Bash-API), запускается по SSH от пользователя `deploy` — учётные данные лежат только на сервере, в GitHub им не место). Хост `<поддомен>.[dev.]wlg.tv` создаётся сразу с сертификатом Let's Encrypt (HTTP-01), форвардится на алиас и порт сервиса.
  Синхронизация идемпотентна: расхождения (`forward_host`, `forward_port`, отсутствие сертификата) исправляются, а хосты, которые стек больше не объявляет в `target`, удаляются — за состоянием стека следит файл `/data/apps/<стек>/.npm-hosts`.
  При отсутствии `target` сервис запускается в полностью изолированном headless-режиме: override удаляется, а ранее созданные для этого стека proxy hosts снимаются с NPM.
- **Изоляция сетей (своя сеть на стек)**:
  Сеть стека создаётся деплоером (`docker network create`) и подключается к ней только Nginx Proxy Manager и сервисы из `target`; остальные сервисы стека остаются в собственной сети compose (`<стек>_default`). Стек не видит контейнеры других стеков, а общая `proxy-network` на сервере больше не используется.
  Известные исключения (сознательные): Nginx Proxy Manager подключён ко всем сетям стеков и остаётся точкой входа между ними; при `monitor: 'true'` стеки дополнительно оказываются в общей сети `monitor_default`.
- **Порты не публикуются на хост**:
  Пайплайн добавляет в override `ports: !reset []` для сервисов, у которых в compose объявлены порты (штатный тег compose, требует compose ≥ 2.24 на сервере). Наружу торчит только Nginx Proxy Manager, трафик идёт по домену. Побочный эффект: стеки больше не конфликтуют за один и тот же порт хоста.
- **Обновление без `docker compose down`**:
  Редеплой идёт через `docker compose up -d --remove-orphans`: работающие контейнеры не перезапускаются без причины, при ошибке `pull` старая версия продолжает работать. Перед стартом вычищаются контейнеры с тем же префиксом имени, но принадлежащие чужому compose-проекту (наследие старого деплоера).
- **Подключение мониторинга (opt-in)**:
  При `monitor: 'true'` пайплайн дописывает в `docker-compose.override.yml` второй блок: внешнюю сеть монитора (`monitor_default`) для всех сервисов стека и `OTEL_EXPORTER_OTLP_ENDPOINT` (`otel-collector:4318`). Compose юзера не трогаем. Если сети нет на сервере — деплоим без monitor-блока с варнингом в summary: наблюдаемость не валит приложение.
- **Атомарность обновлений**:
  Файл конфигурации загружается как `docker-compose.yml.new` и заменяется командой `mv`, что исключает поломку работающего стека при сетевых сбоях.

## Секреты и доступы

### Центральный репозиторий (`wlgdev/deploy`)

- `DEPLOY_SSH_HOST` — IP-адрес или домен сервера.
- `DEPLOY_SSH_PORT` — порт SSH (необязательно, по умолчанию `22`).
- `DEPLOY_SSH_USER` — пользователь сервера (необязательно, по умолчанию `deploy`; если значение — обычное слово вроде `deploy`, GitHub замаскирует все его вхождения в логах, поэтому лучше не задавать).
- `DEPLOY_SSH_KEY` — приватный SSH-ключ пользователя `deploy`.
- `ORG_READ_PAT` — GitHub Personal Access Token (Classic, область `repo`) для клонирования репозиториев организации.
- `GHCR_USER` (variable) — имя пользователя для доступа к реестру контейнеров.

### Клиентский репозиторий

- `DEPLOY_TRIGGER_PAT` — Fine-grained Personal Access Token с правами `Actions: Read and Write` исключительно к репозиторию `wlgdev/deploy`.
